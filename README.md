# dev

tmux workspace launcher for Claude Code agents: project picker, git worktrees, agent-state sidebar, session restore. Single Go binary on top of tmux.

Status: in daily use. It replaced the bash `dev` scripts with strict parity, then added notifications, Codex agent state, Claude resume after restore, session cost and the `dev agent` control CLI.

## Install

```bash
go install github.com/ppf/dev@latest
```

`dev --version` prints the installed version.

## Usage

Projects live in `~/.config/dev/projects.toml` (`[[project]]` entries with `name`, `path`, `description`).

```bash
dev                         # picker: ⏎ opens or attaches the project's boss (see Coordinator view), ctrl-o its plain session
dev <project>               # open the project's main checkout; attaches if the session exists
dev <project> <worktree>    # open <repo>/.claude/worktrees/<worktree>, creating it if missing
dev list                    # name<TAB>description<TAB>path
```

`dev <project> <worktree>` names the session `<project>-<worktree>` (`/` becomes `-`) and attaches when it already exists. A new worktree checks out an existing branch of that name as-is, otherwise branches from `origin/HEAD`, and copies the gitignored files listed in `.worktreeinclude`. Names may only contain `A-Za-z0-9._/-`.

Shell completion covers subcommands, project names and a project's worktrees:

```bash
dev completion zsh > "${fpath[1]}/_dev"   # zsh; see dev completion --help for bash, fish, powershell
```

If `dev` is a zsh alias rather than the binary on `PATH`, also `setopt completealiases`.

## Notifications

`dev state` (the Claude hook) sends a macOS notification through [terminal-notifier](https://github.com/julienXX/terminal-notifier) (`brew install terminal-notifier`) when Claude needs input or a decision (permission prompt, question) or fails; a finished turn doesn't notify. It skips a pane you're looking at: its window is current, not zoomed onto another pane, and a focused tmux client shows it. That needs `set -g focus-events on`; without it every pane counts as not in view. A click switches to the pane and raises the terminal app that started tmux.

```bash
tmux set -g @dev_notify off                                # turn off (or per session with -t)
tmux set -g @dev_notify_activate com.mitchellh.ghostty     # app a click raises
```

dev needs terminal-notifier 3.0 or later (native, built on UserNotifications). If notifications stop appearing, `terminal-notifier -diagnose` reports why (permission, alerts, alert style). macOS's Rosetta warning ("will not open in macOS 28") about terminal-notifier comes from an Intel copy another tool installed through RubyGems (`terminal-notifier` 2.0.0 gem), not from the Homebrew one dev runs.

Set Claude Code's `"preferredNotifChannel": "notifications_disabled"` (in `~/.claude/settings.json`) to avoid duplicate notifications. Hook errors go to stderr, which Claude Code hides for a successful hook; run `claude --debug` to see them.

A claude the pane's Claude runs itself (`claude -p` from its Bash tool) inherits the pane's `TMUX_PANE`. `dev state` records the hook's Claude process (`CLAUDE_PID`, `@agent_pid`); it and `dev question` ignore hooks from a claude running below it: they change no state and send no notification or boss note. A new Claude in the pane (after `/exit` or a crash) registers as before.

## Codex state

Codex CLI hooks give Codex panes the same sidebar state and notifications (needs approval). In `~/.codex/hooks.json`, call `dev state --codex <state>`:

| Event | State |
|---|---|
| `SessionStart` (matcher `startup\|resume\|clear`) | `idle` |
| `UserPromptSubmit`, `PostToolUse` | `working` |
| `PermissionRequest` | `waiting` |
| `Stop`, `Interrupt` | `idle` |
| `SessionEnd` | `clear` |

```json
{"hooks": {"Stop": [{"hooks": [{"type": "command", "command": "$HOME/go/bin/dev state --codex idle"}]}]}}
```

Codex runs hooks in its shared app-server daemon, whose `TMUX_PANE` is the pane that started it, so `--codex` picks the only pane running `codex` (or `codex-*`) whose directory is the hook's `cwd`. Nothing is recorded when no pane matches (Codex's background memory agent, a session started with `codex -C <other dir>`) or two or more Codex panes share a directory. A Codex session outside tmux (the desktop app) in a directory with a Codex pane counts as that pane's. Codex asks you to trust new hooks once (`/hooks`). With `approvals_reviewer = "guardian_subagent"` a reviewer, not you, answers approvals, so leave out `PermissionRequest`. Turn off Codex's own notifications (`[tui] notifications = false`) to avoid duplicates.

## Grok state

Grok CLI hooks give Grok panes the same sidebar state, notifications and boss notes. Grok runs hooks in the pane's own process (its default shell route; its `grok host-server` daemon route isn't supported), so plain `dev state` finds the pane through `TMUX_PANE`; it knows a Grok hook by `GROK_HOOK_EVENT` and then leaves out subagent events (`subagentType`) but their permission prompts and questions, and the extra `Stop` at session end, records no session (Grok panes aren't resumed) and never answers as a boss. In `~/.grok/hooks/dev.json`:

| Event | State |
|---|---|
| `SessionStart` | `idle` |
| `UserPromptSubmit`, `PostToolUse`, `PostToolUseFailure` | `working` |
| `Notification` (matcher `permission_prompt\|elicitation_dialog\|idle_prompt`) | `waiting` |
| `Stop`, `StopFailure`, `StopCancelled` | `idle` |
| `SessionEnd` | `clear` |

```json
{"hooks": {"Stop": [{"hooks": [{"type": "command", "command": "$HOME/go/bin/dev state idle", "timeout": 10}]}]}}
```

Grok also runs the hooks in `~/.claude/settings.json`, so turn that off (`[compat.claude] hooks = false` in `~/.grok/config.toml`) to keep Claude's hooks from recording twice, and turn off Grok's own notifications (`[ui.notifications] condition = "never"`) to avoid duplicates. A Grok pane is one running `grok` (or `grok-*`, its versioned binary). Grok can report an interrupted turn after the next prompt started, so `dev state` keeps the `promptId` of the pane's latest `UserPromptSubmit` and ignores a `Stop`, `StopFailure` or `StopCancelled` for another turn.

## agy state

Hooks of agy (Antigravity's CLI) give agy panes the same sidebar state, notifications, decisions and boss notes. agy runs hooks in the pane's own process, so `dev state --agy` finds the pane through `TMUX_PANE`. agy fires no hook per prompt: a turn starts at its first model call (`PreInvocation` with `invocationNum` 0, which also counts the prompt for `prompt --wait`) and ends at `Stop`. The conversation (`conversationId`, `transcriptPath`) is recorded as the pane's session, but agy panes aren't resumed. Add these to `~/.gemini/config/hooks.json` yourself (dev doesn't write it; a hook set in a workspace's `.agents/hooks.json` loads only once you trust that folder):

```json
{"dev": {
  "PreInvocation": [{"type": "command", "command": "$HOME/go/bin/dev state --agy working", "timeout": 10}],
  "PreToolUse": [{"matcher": "*", "hooks": [{"type": "command", "command": "$HOME/go/bin/dev state --agy working", "timeout": 10}]}],
  "PostToolUse": [{"matcher": "*", "hooks": [{"type": "command", "command": "$HOME/go/bin/dev state --agy working", "timeout": 10}]}],
  "Stop": [{"type": "command", "command": "$HOME/go/bin/dev state --agy idle", "timeout": 10}]
}}
```

`dev state --agy` prints nothing, ever: agy reads a hook's stdout as its decision (`{}` on `PreToolUse` denies the tool call). Any other agy event (a later model call, a tool call; a tool call's end unless it settles a decision, below) only stamps activity; a hook fired outside tmux, or by an `agy -p` another agent runs in its pane, does nothing, and a failing one reports on stderr, never through its exit status. agy fires no hook when you decline a permission prompt or press Esc: the turn ends on screen, `⎿ Interrupted · What should Antigravity CLI do instead?` right above its input box, so `prompt`, `wait` (every second) and the boss inbox's stuck check record the pane idle from its screen, as for Claude's Esc (see [Driving agents from an agent](#driving-agents-from-an-agent)). agy fires no hook before its first turn either, so `dev agent start` records a new agy pane idle once its input box shows; a screen it left to you (see below) gets no state until you answered it and ran the start again (`wait` and `prompt --wait` refuse it meanwhile). It does so only when the workspace's `.agents/hooks.json` or `~/.gemini/config/hooks.json` run `dev state --agy` at `PreInvocation` and `Stop`, not `"enabled": false` (dev only reads them; one it can't parse it names on stderr), else it records nothing and says so: send with plain `prompt` and `read`. Its decisions show as Claude's do (see [Driving agents from an agent](#driving-agents-from-an-agent)): `waiting`, a `needs a decision` note to its boss, NEEDS YOU on the boards, refused by `prompt`. A question is its `PreToolUse` of `ask_question`, which carries the question, its options and whether it takes several: recorded as the pane's `@agent_question` (`get --json` lists it under `questions`), the note asks it. agy fires no hook for a permission prompt, and the same `PreToolUse` for a call it runs at once: each other tool call's `PreToolUse` starts `dev agy-dialog` in the background, which reads the screen for 5 s and, once it shows `Requesting permission for:` over a question and numbered options with `esc to cancel` in the input box's place, records the pane waiting on it (its tool and command, `allow Bash: echo hi` in the note); its errors go to `agy-dialog.log` in dev's state directory. A boss's inbox check reads its working agy workers' screens for one too, and a waiting one's every round. The turn goes on once agy's input box is back: an approved command at once (`dev agy-dialog` watches the prompt it recorded), an answered question at its `PostToolUse` (or, if agy hadn't drawn the box again by then, from its screen); a cancelled or declined prompt, which fires none, settles to idle from its screen as above, a question's skip (Esc) fires `PostToolUse`. agy's lists take an option's digit alone (no Enter), and Esc. A turn's end note carries agy's last reply, read from the end of its transcript (`transcriptPath`, written before its `Stop`); a `Stop` whose `error` is set, or whose `terminationReason` is `ERROR` (or `TERMINATION_REASON_ERROR`) (agy's `TERMINATION_REASON_ERROR`; only `NO_TOOL_CALL` was seen), ends it as failed, as Claude's `StopFailure`. `prompt` and `prompt --wait` also refuse an agy pane whose screen shows no input box (a dialog dev didn't record), and press no Enter after the paste unless agy's input box still shows then (the text stays in agy's input box; this narrows the window, it can't close it). A pane runs agy when its command is `agy`.

## Session restore

The `dev resurrect` [tmux-resurrect](https://github.com/tmux-plugins/tmux-resurrect) hooks bring back each session's `@project` and sidebar, and each agent's own Claude conversation: `dev state` records the hook's `session_id` and transcript on the pane, the save keeps them next to the snapshot, and the restore types `claude --resume <id> --remote-control=<session>` (a worker's without Remote Control, see [Remote Control names](#remote-control-names)) into each agent pane it brought back as a bare shell (100 ms apart; sessions that were still running are left alone). A pane restored into another directory, or whose transcript is gone, gets a fresh agent and a warning. An agent started with `--model` or `--effort` (`dev agent start`, `dev boss`) keeps them: `claude --resume` keeps the conversation's model but takes your default effort, so the restore passes `--effort` again, and `--model` too to a fresh agent. Codex panes aren't resumed. A boss comes back as a boss (only a session the save recorded as one, by the `@dev_herd` mark and its panes' `@dev_boss_pane` roles; a boss made before dev recorded those comes back plain, as does one whose panes didn't come back as bare shells, with a warning and its coordinator resumed as a plain agent): marked again, its coordinator resumed into its conversation (fresh otherwise) with the coordinator prompt (the manager with its own), its previews and sidebar back, so `dev boss <project>` and the picker attach it (a `boss` session from before dev required a project is reached through the sidebar or `dev goto`).

```tmux
set -g @resurrect-hook-post-save-layout '$HOME/go/bin/dev resurrect save'
set -g @resurrect-hook-post-save-all '$HOME/go/bin/dev resurrect prune'
set -g @resurrect-hook-pre-restore-all '$HOME/go/bin/dev resurrect pre-restore'
set -g @resurrect-hook-post-restore-all '$HOME/go/bin/dev resurrect restore'
```

Keep claude out of `@resurrect-processes` and `@resurrect-default-processes` (and off `:all:`): resurrect would start its own claude in the same pane, so dev warns and resumes nothing.

A session you close with the sidebar's `x` or `×`, the boss previews' `x`, or `dev agent close` stays closed: once it's gone, dev saves a snapshot without it (`dev resurrect snapshot`; dev's saves take turns, each in a second of its own, as resurrect names snapshots by the second), so a restore after a reboot leaves it out. A save in the second of another (tmux-continuum's autosave or `prefix + C-s` right after one of dev's) rewrites that second's file, and resurrect would find it identical to `last` (itself) and delete it, leaving `last` dangling and a restore before the next save empty: the `dev resurrect save` hook above, which every save runs, unlinks such a `last` (after a dev snapshot in progress has linked it), so resurrect links it again. A save that waited there for dev's snapshot leaves `last` on it when it is the later one, so an autosave begun before a close can't bring the closed session back. No other config needed. Resurrect has no hook before it writes a snapshot, so two saves started at the same moment (both writing one file) or two saves outside dev ending together can still clash. The sidebar closes the last session too: dev turns tmux's `exit-empty` off until that save, then back on, so the server exits and the next `dev` restores nothing (with `exit-empty` already off, the server stays up empty). A session you only detach from (closing the terminal tab) stays in the snapshot; one that ends by itself (`exit` in its last pane) leaves it at the next save (tmux-continuum's autosave, every 15 minutes by default). A session whose Claude exits cleanly (`/exit`, Ctrl-D: status 0; dev starts it under `dev pty-wrap --close-on-exit`) closes like `×`, asking about its worktree on a client attached to it (with none attached, the worktree stays); a crash or a shutdown leaves it for the restore. Every close (the sidebar's `x`/`×`, the previews' `x`, `dev agent close`, such an exit) writes an archive record, `$XDG_STATE_HOME/dev/archive/<session>[.N]/session.json` (`.2`, `.3`, … for a reused name): project, path, the last Claude conversation and transcript (to resume by hand with `claude --resume`), the worktree and whether it was removed.

## Driving agents from an agent

`dev agent` lets one Claude session (a coordinator) drive the agents in other sessions. Targets are session names or pane ids (`%12`), never sidebar positions.

```bash
dev agent list [--json]                        # session, pane, agent, state, branch, path, cost
dev agent list --mine                          # only the workers this session started (its child sessions)
dev agent start <project> [<worktree>]         # open detached, return once its Claude registered
dev agent start <project> [<worktree>] --agent codex  # a new session runs codex; returns once codex runs
dev agent start <project> [<worktree>] --agent grok   # same with grok
dev agent start <project> [<worktree>] --agent agy [--model <slug>] [--effort high]  # agy; returns once its input box shows, or (exit 0, ⚠ on stderr) on a screen it leaves to you
dev agent start <project> [<worktree>] --model sonnet --effort medium  # a new session's Claude starts with them
dev agent start <project> [<worktree>] --agent codex --model gpt-6-luna --effort high  # a new session's codex too
dev agent prompt <target> --wait "Fix the test" # paste + Enter; --wait returns when the turn ends
dev agent prompt <target> --wait /clear        # reset its context; --wait returns once the new session started
dev agent wait <target> [--until idle|waiting|settled] [--timeout 90s]
dev agent wait-until 16:30 "Codex limit resets" [--on <worker>]  # a planned wait: dev wakes it then (+90m too; ≤4h)
dev agent wait-until --cancel [--on <worker>]  # end it without a prompt
dev agent read <target> [--lines 50]           # the pane's screen (plus scrollback, if any)
dev agent send-keys <target> esc|enter|ctrl+c|1|…
dev agent close <target> [--json]              # close a finished worker: session, worktree, branch
dev agent clear <boss> [--facts <file>] [--force]  # clear an idle boss's context: handoff, verify, /clear, proof
dev agent message <boss> "text" [--fyi]        # message another boss (or manager); prints its id (m12)
dev agent reply <id> "text" [--done]           # reply in its thread; --done ends it
dev agent messages [--json]                    # threads: a boss's own; every thread elsewhere
dev agent handoffs [--json]                    # what the manager sent its bosses by --kind, ungated first, with counts
dev delivered <worktree> [--json]              # close's delivered checks only, for a desktop-app boss: exit 0 if delivered
dev agent skill > ~/.claude/skills/dev-agents/SKILL.md   # the coordinator skill
dev agent skill desktop-boss > ~/.claude/skills/desktop-boss/SKILL.md   # its desktop-app twin (start_session, SendMessage)
```

`start`, `list --mine` and `close` act for the session they run in (`TMUX_PANE`). A coordinator outside tmux (e.g. a Claude desktop-app session) passes `--boss <session>`, naming a `dev boss` session to act as: its workers are the same as the ones its coordinator starts (nested under it in the sidebar, previewed, no Remote Control, notes to its inbox), and `close` runs the same checks. Any other session is refused. Such a worker is the outside coordinator's, not the boss's own coordinator's: `start` marks it `@dev_started_outside` (`outside: true` in `list --json`), each note the boss's inbox gets about it ends in "started by a coordinator outside tmux: leave it to that coordinator", and `close` refuses it unless run with `--boss` outside tmux. Its new session takes the boss's window size (a desktop app's Bash tool has no terminal to size it from); without `--boss`, a caller with no tmux client or tty takes the widest attached client's.

`start --model <alias or id>` and `--effort low|medium|high|xhigh|max` start a new session's Claude with them (`claude --model`, `--effort`), so a coordinator picks them per worker; without them it runs on your settings. With a session that exists they are an error, naming what it was started with, unless they equal that (so a retried start is accepted; a flag left out isn't compared), and with `--agent grok` always: never ignored. `--agent agy` takes them too (`agy --model`, `--effort`): agy would start on its stored model if it didn't know the slug, saying so only on its screen, so dev refuses a `--model` that `agy models` doesn't list. A new agy session in a worktree this start made shows agy's trust dialog for that folder, which dev confirms ("Yes, I trust this folder"; agy adds it to `trustedWorkspaces` in `~/.gemini/antigravity-cli/settings.json`); in the main checkout or a worktree that was there before, dev leaves it to you at once, and a login screen or any other dialog once `--timeout` passed, saying so on stderr (exit 0); once you answered it, run the same start again to record agy idle. dev never starts agy with `-i`, `--dangerously-skip-permissions` or `--mode`. With `--agent codex` they start codex with `-m <model>` and `-c model_reasoning_effort=<effort>` (codex has no effort flag; the override runs codex without its shared background server, a startup warning on its screen), `--effort` one of `low|medium|high|xhigh|max|ultra`. Codex starts anyway on a model its account doesn't list (a warning on its screen) and on an effort the model doesn't take (on another model or effort, silently), so dev first checks `--model` against `codex debug models` (its model catalog, no quota used) and `--effort` against that model's levels, and refuses either; a new Codex session's `--effort` needs `--model` (the default model is codex's own pick, and each model takes its own efforts). dev records them on the session (`@dev_model`, `@dev_effort`): `list --json` and `get --json` show them as `model` and `effort`, and the `dev resurrect` restore keeps a Claude agent's (Codex panes aren't resumed; see [Session restore](#session-restore)). `dev boss` takes the same two flags for a new boss's coordinator.

Exit status: 0 ok, 1 error, 2 timeout (still working: `working: still at it after <timeout>; wait again or read it` on stdout, nothing on stderr), 3 stalled (the prompt was never picked up). State comes from the `dev state` hooks, so `wait` and `prompt --wait` refuse a Codex pane without them. `prompt` refuses an agent showing a permission prompt or question (`@agent_waiting_for`, the Notification type), and `prompt --wait` counts prompts through the `UserPromptSubmit` hook (`@agent_prompts`), so the hook must run this version of `dev`. `/clear` (and its aliases `/reset`, `/new`) starts no turn, so `prompt --wait /clear` waits instead for the `SessionStart` of the new conversation (a new `@agent_session`, which Codex and Grok panes don't record and agy's records only from its first turn, so they refuse it). `agent` is a subcommand, so no project can be named `agent`.

`wait-until` plans a wait for a known time (a usage or rate limit's reset, a scheduled job), so a worker needs no background `sleep` and its boss no check-ins: run by the worker itself (its `TMUX_PANE`) or by its boss with `--on`, on a Claude worker a boss with its inbox on started (else nothing would wake it). The time is a local `HH:MM`, the next one (00:30 at 23:00 is tomorrow's), or `+<duration>`; more than 4 hours away is refused, so a wait can't hide a real problem; a reason may not hold control characters or end in `;`. It's kept on the agent pane (`@dev_wait_until`, `@dev_wait_reason`, and `@dev_wait_prompts`, the `@agent_prompts` then, moved along by its own background tasks' turns); a new one replaces it. While it holds: the boss's inbox sends no `stuck` note for a worker resting or parked on background tasks (one still working gets them), no idle PR check and no repeat of its question; a dialog still makes `needs a decision`. The previews card sits in WAITING and says `until 16:30 · Codex limit resets`, the sidebar row says it in place of the state, a to do item on it says `waiting until 16:30`, and `list`/`get --json` carry `"wait": {"until", "reason"}`. A turn ending in one sends the boss `waiting: until 16:30 (Codex limit resets), dev wakes it then` in place of `finished`, and ends a run of rate limits as any finished turn does; a rate limit's resume scheduled before waits for the wait's time. When it's due, the boss's previews send the worker `Your planned wait until 16:30 (Codex limit resets) is over: continue where you left off.` if it's idle with an empty input box, and queue `resumed: its wait until 16:30 (Codex limit resets) ended, dev sent it: continue`; a draft in its input box keeps the wait for the next round, with one `failed: waking it after its planned wait: its input box holds a draft, not woken yet` note, and the usual rules apply again. Due while on a dialog or working, or a turn ending past its time, it's dropped and the usual rules apply (the stuck clock starting at its end). Any prompt ends it (its `UserPromptSubmit` hook), as does `--cancel`, but not the turn its own background task's end starts (Claude Code's `<task-notification>` prompt, or a subagent's `[Subagent hand-back]` message): its last such turn ends on the waiting note again; a closed worker takes it along, and the `dev resurrect` restore puts it back (due while the server was down, it wakes the worker at once). In a desktop app session the worker sets its own (no `--on`), in its hook file (refused without one: its `dev state` hooks don't run): `dev desktop board` shows it as `waiting` with the same text and `wait` while the worker is idle or busy with its own background tasks, sends no `stuck` note for those meanwhile and a `wake due` note at its time, for the boss to message the worker; a prompt (not a background task's end) or a turn ending past its time ends it.

Some changes run no Claude hook, so `dev agent` reads them off the screen:
- A Claude waiting on an `AskUserQuestion` dialog: `get`/`list --json` show every question of it (each tab, not only the open one) as `questions`, each `{header, question, multi_select?, options: [{label, description?, recommended?}]}`, from its `dev question` hook; `recommended` marks an option whose label says "(Recommended)", Claude's label convention. A permission prompt has none.
- A prompt to a working Claude is queued: `prompt` prints `queued: …`, and `get`/`list --json` show `"queued": true` while the input box says `Press up to edit queued messages`. The `UserPromptSubmit` hook fires at queue time, so `@agent_prompts` can't tell when it's read.
- `get --json` gives a Claude pane's input box as `input: {text, suggestion}`: `suggestion` is true when all of it is Claude Code's own dim text (a prompt suggestion such as `run it`, a placeholder, or a hint such as `Press up to edit queued messages`), which `capture-pane -e` keeps and the user never typed; `read` ends that row with `  [suggestion]`. No `input` while a dialog stands in the box's place.
- A one-line slash command Claude runs itself (`/effort`, `/model`) counts no prompt. `prompt` watches the screen for up to 3 s (an error if it isn't seen running): the dialog both open mid-conversation (`This conversation is cached …`) is confirmed with `1` once it shows; any other dialog is an error (read it, answer with `send-keys`). `--wait` returns once the input box is back, idle, without the command; a command that starts a turn (a skill's) waits like any prompt.
- Esc ending a turn: the working state is recorded idle once the screen shows `⎿ Interrupted` above an idle input box. `send-keys esc` to a working Claude waits up to 3 s for it, and `prompt`, `wait` (every second) and the boss inbox check for it too; `prompt`, `wait` and the inbox check an agy pane too (not `send-keys esc`), whose Esc or declined permission prompt ends the turn so (see [agy state](#agy-state)).
- Claude's agent panel under its status lines (`⏺ main`, a `◯` row per teammate or background agent) isn't taken for the end of its input box.

`close` ends a worker whose work is delivered: the caller's own worker, or one nobody started (a plain terminal or the desktop app; any coordinator, or a plain terminal outside tmux, may close it), never one another session started, or whose starter session is gone (its `@dev_started_by` names it), nor its own session, idle or waiting only because it sat idle, in a `.claude/worktrees` worktree no other session has a pane in, with no changes to tracked files and its HEAD in origin's default branch (local `origin/HEAD`, after a fetch; in a repo without an `origin` remote, the branch checked out in the main checkout; checked with `git merge-base --is-ancestor`, as `git branch -d` refuses when the branch's own remote ref is stale). Otherwise HEAD must be the head commit of a PR/MR that is open, or merged into that branch (a squash or rebase merge leaves its commits out of it): looked up by commit in origin's repository (`gh api repos/<owner>/<repo>/commits/<HEAD>/pulls` for a github.com origin or one on a host `gh` is signed in to, else `glab api …/repository/commits/<HEAD>/merge_requests`), so on GitHub a PR from origin, a fork, to its upstream counts. A commit after the PR's head is refused. Without `gh`/`glab`, or when it fails, such a worker is refused with its error. Anything else is refused, naming the failed check, before it touches the worker. It copies the worktree's untracked, not ignored files (e.g. `RESULT.md`) to `$XDG_STATE_HOME/dev/results/<session>/` (`<session>.2`, … when that exists) and prints where; other ignored files go with the worktree, but a git-ignored `RESULT.md` is refused unless that folder already holds the same text (the refusal says where to copy it). It moves clients watching the worker to the caller's session, kills the worker's session, removes its worktree and force-deletes its branch. Claude Code's auto mode blocks a coordinator's raw `tmux kill-session` and `git worktree remove`; allow `Bash(dev agent close:*)` instead.

`clear <boss>` clears a long-lived boss's context without losing what it must remember, for the session that started or adopted it, its manager (in a Claude Code session, only that session), or you in a shell; a boss never clears itself. It takes minutes, so an agent runs it in the background. It is refused, naming every failed check, unless the boss's hook records its session and transcript, it is idle with an empty input box, no other `dev agent clear` runs for it, none of the sessions it started is working, without an agent or hook state, or waiting on a decision, no inbox note waits for it, no planned wait or rate-limit resume is ahead for it or a worker, and its context share (`@agent_context`, from `dev statusline`) is at least 20% (`--force` skips only this check, also with the share unknown); open asks to you don't block it. From the save on, the boss's inbox notes are held back until the command ends (`@dev_handoff` names its process; a note that came in refuses the clear at the second check). Then it prompts the boss (each prompt only into an empty input box; a turn ending on a permission prompt or dialog stops it) to update its list and notes and write a handoff, `$XDG_STATE_HOME/dev/handoff/<boss>/<time>.md`, with fixed sections (key facts, numbered, at most 15, each ending `unconfirmed` or, as a last clause, `confirmed: …`; open asks and what each pick starts; work in flight; your standing words; roles: who answers its workers' prompts and dialogs, who relays its asks; open risks; the old transcript's path), copying in the caller's `--facts` file word for word (refused up front when one of its facts is unmarked, worded as done while `unconfirmed`, numbered twice or over 15). dev verifies it (every section, something under roles, marked facts each under its own number, no `unconfirmed` fact worded as done, by words only: a done word such as merged, released or fixed with no hedge such as reported, not, may or pending, every open item's number, the transcript path, each `--facts` fact, and no item of yours or a person's without details on the list), prompting the boss once to fix a miss and stopping, nothing cleared, on a second. With the checks passed again, and right before it the boss still in the conversation that saved, with no turn since and an empty box, it sends `/clear` (confirmed by the new session); the fresh boss's start hook adds the handoff's path to its list and notes. Last, it prompts for a proof file, `<time>-proof.md`, written before touching any worker (each fact restated with its mark, what it does on each open ask's pick, who answers its workers' prompts and relays asks), and checks every fact and open ask is there, prompting once with what is missing. It prints the handoff, proof and old transcript paths (a failure after the `/clear` prints them with the proof prompt to send by hand): dev checks form, the caller judges meaning. The files stay on disk. The clear's own prompts aren't recorded in `dev agent handoffs`: they are dev's fixed text, not the manager's. dev offers the clear itself: once per idle stretch, a boss that rested 30 minutes with every check passing (context 20% or more), or 2 minutes at a context of 40% or more with none of its asks up in the manager's question dialog, is noted to the manager that started or adopted it (`may be cleared: … clear it?`), which runs it itself, without asking you (no new offer for 30 minutes after one); for the manager itself (also after 2 quiet minutes at 40% or more) the offer is an ask on its own list for you (NEEDS YOU), to run `dev agent clear manager` from a plain shell (a clear that passes answers it). A boss with no live manager over it gets no offer.

`dev delivered <worktree>` runs close's checks of the work alone (HEAD in the default branch or at an open or merged PR/MR, no changes to tracked files) on a `.claude/worktrees` worktree, with no tmux, touching nothing but the fetch of origin, e.g. for the desktop-boss skill before `archive_session`. Delivered: exit 0 and `delivered: <head> (PR #12 open|PR #12 merged|in origin/main)` (`MR #12 …` on GitLab, `in main` without an origin remote); else exit 1 and the failed check. `--json` prints `{delivered, head, reason, pr}` either way (`pr` only when a PR/MR delivers it, `head` once read). `delivered` is a subcommand, so no project can be named `delivered`.

## Coordinator view

```bash
dev boss <project>      # open or attach the project's boss session, "boss-<project>"
dev boss                # no project: open or attach the manager, a boss over the bosses (session "manager")
dev boss <project> --background   # create it detached (no attach), started by the calling boss; prints boss-<project> once its Claude registered; an existing boss is only printed
dev boss <project> --background --adopt   # in the manager's pane: make an existing boss with no parent the manager's
dev boss <project> --model opus --effort medium   # a new boss's coordinator starts with them
dev boss <project> --no-serve   # don't start dev serve (the phone page); also DEV_NO_SERVE=1
```

Bare `dev` (and the sidebar's picker) is a project picker for `dev boss <project>`: `⏎` opens or attaches the boss, `ctrl-o` the project's plain session instead (`dev <project>`, main checkout); a worktree is `dev <project> <worktree>`. Inside tmux it runs in a popup and switches your client to the chosen session; `dev new` and prefix+0 open it too. A boss in `$HOME` takes a project with `path = "~"` in `projects.toml`.

`dev boss` with no project opens or attaches the manager: a boss whose workers are bosses, in the same layout (coordinator, previews, sidebar), session `manager`, started in `~/.config/dev/manager` (made empty; a `CLAUDE.md` there is its own rules, never a project's). You tell it what to start or ask; it starts bosses with `dev boss <project> --background` (on their project's settings), takes over one you opened yourself when you ask (`--adopt`: only a boss no live session started; from then its news goes up to the manager, it shows in the manager's `--mine` list and previews, and it keeps its workers and list), closes one of its own when you ask (`dev agent close boss-<project>`: refused unless the boss is idle, no session it started is left and its list has no open ask; it closes as × does and the list stays; × on its sidebar row closes any boss), relays what they send up (what waits on you, asks, decisions, failures) and forwards questions between them. Your own new idea or request for project work it first assesses (sound or not, pros, cons, what it conflicts with on the bosses' lists, a recommendation): before every hand-on of new work it asks you, with the assessment and the brief it would send, the assessment and its cons in it ("Hand it on" / "Drop it"; Drop it or skipped, it isn't handed on; text under Other is a correction it revises and asks again), and the boss gets your own words. Not asked: relaying your pick on an item, a question to a boss about state or a fact, its own easy decisions (new work never is one), your dev commands. dev checks it: the manager's `dev agent prompt`, `message` and `reply` to a boss need `--kind` (`work`, `question`, `pick` or `own`), and `--kind work` passes only when your latest pick there, typed messages since or not, is "Hand it on" on one question whose first line starts "Hand on to <boss>" and that holds the brief's first line as a line of its own, once per pick (a typed message with no pick, "Drop it", text under Other or a pick for another brief or boss is refused; a new hand-on question drops the pick; words you type after it that withdraw or change it make the manager ask again; a send refused before it reached the boss gives the pick back). A typed go passes too: when your latest message, typed by you, follows the manager's assessment of that very work in its previous reply and names or plainly answers it ("Tak ruszaj" to "start it today?"), it hands it on with `--kind work --go '<your words, quoted>'`, which dev lets through only when the words stand in your latest message in the manager, that message is typed by you (by the transcript's record: not an inbox batch, another session's message, a plugin's prompt, a task's end, an accepted suggestion, text only pasted or a pick) and it wasn't used for a send before, nor a question (AskUserQuestion) asked after it; words about something else, a conditional or a question are no go, and the manager asks with the hand-on question. A plain command of yours passes at once: when your latest message, typed by you, tells it to do a piece of project work and it has no objection and sees no conflict on the bosses' lists, it hands it on in that turn with `--kind work --command '<your words, quoted>'`, your words word for word, and says so in one line (`Handed on to boss-<project> as you said ("<your words>"); no objection, no conflict on its list.`); dev checks it as a typed go, and also refuses a message holding a `?` outside a URL. Ideas, conditionals, questions, anything it objects to or that conflicts with a boss's list, additions to work handed on and its own additions are still asked. `dev agent handoffs` lists each send (kind, time, target, first line; a typed go or command with your words) and each dropped, corrected or refused hand-on question (refused: your "Hand it on" click the gate refused), ungated sends first, under the trial's counts (gated, typed go, command, ungated per kind, dropped, corrected, refused; a dismissed question isn't seen). It manages, the bosses work: it reads only dev's own state and what a boss delivered, hands any question that needs a project's Slack, PRs, repo or records to that project's boss, and starts with the claude.ai connectors off (`--settings '{"disableClaudeAiConnectors":true}'`). It puts what waits on you to you with AskUserQuestion, up to 4 independent asks in one dialog and a hand-on question always alone (its bosses' open asks, a boss's permission prompt or dialog, its own decisions) and relays your pick (`dev todo answer --via manager`, below; `send-keys` for a dialog), but never answers a permission prompt, a dialog or an item on its own, merges or acts outside dev; a question you skip, except an assessment one, stays open on the sidebar's TO DO, the desktop board and `dev todo answer`. A new manager runs on `opus` with `medium` effort unless `--model` or `--effort` say otherwise (`dev resurrect` keeps them). Claude Code compacts the manager's conversation by itself at 300K tokens (`claude --autocompact`, Claude Code v2.1.221 or later): set `manager_autocompact = <tokens>` at the top of `projects.toml`, before the `[[project]]` entries (at least 100000), or `0` for Claude Code's own window, from the manager's next start; bosses and workers keep Claude Code's. After any compaction, a `dev boss` coordinator's own SessionStart hook on `compact` (dev passes it in the coordinator's `--settings`, as your `dev state` hooks match no compaction; adding `compact` to them too would give the context twice) gives it its open list, notes and, while a `dev agent clear` runs, its handoff's line again, leaving its state as it was; the manager first gets what it still owes (a pick not relayed, an item marked asked in it, a hand-on question picked but not sent). With no terminal (stdin or stdout not one, e.g. a Claude's Bash tool) it starts the manager detached when missing, waits until its Claude registered (on timeout, e.g. a first-run trust prompt in the new folder, it prints its screen, as `dev agent start` does) and prints `manager running: dev goto manager`; `dev goto <session>` switches to a session by name (outside tmux: attaches it). No project can be named `manager`.

One window: a coordinator Claude on the left, started in the project's main checkout (default `$HOME`) and told to use the `dev-agents` skill, so its prompt is the one input field ("start workers for X and Y", "tell fix-login to add tests"). A Claude worker's reply and tool call come from its transcript (`@agent_transcript`, which `dev state` records; its last 1 MB, read again only once it changed). An idle card is folded to one row (name, how its turn ended, PR and its checks' icon, `?` after it when the last read failed, ⚠ for a warning, time; the selected one on the selection band) unless it has a warning; an Asking card is never folded. It refreshes once a second, only while its window is on screen, capturing at most 12 panes: the selected card's (open or with a dialog), the ones with a dialog open or an `AskUserQuestion` recorded while working, then the other open cards', nearest the selected one first.

### Reply box

`m` (or `i`, or a card's **Message…**) binds the reply box at the bottom to the selected worker: a rule in the worker's state colour (gold working, red waiting, green idle) naming it with its agent, state and branch, over the draft behind a bar of the same colour. Its card is the selected one, framed in that colour too. The draft grows to 8 rows (fewer in a short pane): `⏎` sends it as a prompt (as `dev agent prompt`, so a worker waiting on a decision refuses it), `alt+⏎` or `ctrl+j` adds a line (so does `⇧⏎` in a terminal sending it as `alt+⏎`, as Ghostty's `keybind = shift+enter=text:\x1b\r` does; tmux passes a bare `⇧⏎` as `⏎`), a bracketed paste keeps its lines, `←`/`→`/`home`/`end`/`ctrl+a`/`ctrl+e` move, `ctrl+u` and `ctrl+w` delete back to the line start or a word, `↑` on an empty draft recalls the last 50 replies (`↓` back), `esc` closes. A draft typed before a dialog comes stays a draft.

When the worker waits on a numbered dialog (Claude's questions and permission prompts, Codex's and Grok's menus), its card shows it in place of its status: for a permission the tool with its command, file or URL, the question tabs, the question, its options side by side (wrapping when narrow; the highlighted one, the box's or else the dialog's own cursor, bracketed in the worker's colour, `[1 Yes]`; a multi-select's ☐/☑ and a `Submit ⏎` after them), then a question's described options as `label: description` (a permission's option shows its whole text); its screen stops above the dialog's tabs or question, keeping what it shows above them (a command, a file's contents, a folder, the answers to review); a question's card (not its review) shows no screen, and no Asking card repeats its note. The board scrolls to keep the box's highlighted option in view. A click on an option opens the card's box and picks it (toggles a multi-select's), on `Submit ⏎` goes on, as the keys do; while an answer is out the options dim and a click says so; over a typed reply it says to send or clear it first. With the box open on the card, the box is the picker's keys: `←`/`→` (or `↑`/`↓`) move, `⏎` or `1`–`9` pick, `space` (or a digit) toggles a multi-select option and `⏎` goes on to the next question or the review, the free-text option ("Type something") takes typed text in the box (`esc` back to the options), `esc` closes; one answer goes out at a time. Each answer first captures the worker's screen and sends nothing if another dialog shows than the one drawn (another question, command, file or checked box); then it presses the keys the dialog takes, 200 ms apart (a digit; Claude's free text: its number, the text, `⏎`; a multi-select's free text: arrows to it, the text; its Submit: arrows to the Submit row, `⏎`), and polls until the dialog changes, reporting a failure after 2 s (and a picker still showing the answered dialog three refreshes later comes back, saying so). A question of several tabs shows them all, the open one first: each later tab as its header, question and options, the ones before it as answered; `★` marks a recommended option (its label says "(Recommended)", Claude's label convention). When every tab from the open one is single-choice, the box answers it whole: each tab starts on its recommended option, `1`–`9` and `↑`/`↓` pick on the marked tab (`▸`, a digit then moves to the next), `←`/`→` move between tabs, and `⏎` sends the picks in one go and submits them on the review; before each tab's key it checks the screen shows that tab's question (the first: the dialog drawn) and stops, saying how many went, when it doesn't. A tab without a recommended option needs a pick first; the open tab's free text answers it alone, as above. The question and options come from the screen; the tabs, full option descriptions and a permission's tool with its command, file or URL come from the worker's `@agent_question` when it matches the screen, which the `dev question` hook records:

```json
{"hooks": {
  "PreToolUse": [{"matcher": "AskUserQuestion", "hooks": [{"type": "command", "command": "$HOME/go/bin/dev question", "timeout": 5}]}],
  "PermissionRequest": [{"hooks": [{"type": "command", "command": "$HOME/go/bin/dev question", "timeout": 5}]}]
}}
```

Claude Code sends `PermissionRequest` (with the tool's input) for its questions and permission prompts, also for a tool auto mode then approves, so the hook only records what a dialog would ask and the picker shows it only while the screen shows that dialog; the `dev state` of the turn's end (or the next turn's start) clears it. Answering `No` or `esc` runs no Claude hook, so the worker stays recorded as waiting. Its screen settles that: once a permission prompt or question has been recorded for 2 s, Claude's own input box back at the bottom (no dialog in its place) has a reply, `dev agent prompt`, `dev agent close`, the previews, the inbox's stuck check and its delivery to the boss record it idle (working while it shows `esc to interrupt`) and clear its question; a dialog still on screen keeps refusing a reply. Claude records a dialog only seconds after drawing it (not while you type in it), so a prompt to a working Claude whose screen shows no input box is refused too. `dev question` prints nothing (Claude reads a `PermissionRequest` hook's stdout as its decision). Without the hook (Codex, Grok, an agy permission prompt, or an older `dev`), the picker shows the screen's options alone; an agy question's hook gives them as Claude's does (see [agy state](#agy-state)).

### Boss inbox

The coordinator hears of its workers on its own: a worker's `dev state` hook queues a one-line note for the boss that started it when the worker finishes (with its last message), fails, or needs a decision (permission prompt or question, saying what it asks: `Which color? (Red / Blue)` or `allow Bash: <command>` from the `dev question` record while the screen shows that dialog, else Claude's own message; a Codex worker's `PermissionRequest`, with the command's description), or, instead of `finished`, ends its turn on a question (`asks: <the question>`, from the last message's last few lines: a line ending in `?`, not a heading, followed only by list items, its options). The previews (every 15 s) add:

- `stuck: no progress for 15m`: a working worker that ran no hook (a finished tool call, its own or a subagent's: `dev state` stamps `@agent_active`, also for a subagent's events) and whose screen didn't change (spinners, timers, clocks, token counts, costs, and Claude's input box and status lines aside) for 15 minutes, however long its turn; a single command running that long without output counts too. One stretch without progress gives one note. The minutes are those when it was queued; the card's note keeps them current. A Claude worker whose turn ends only to wait on background subagents or shells stays working, with no note or notification, until the turn after them ends; one whose input box is back while nothing moves gets `…, waiting on its background tasks` (a hung shell, or a dev server left running).
- `stuck: waiting on a decision for 4m, unanswered`: a permission prompt or question unanswered over 3 minutes.
- `stuck: idle for 15m, PR #12 has merge conflicts` (and/or `no CI checks`): a worker idle about 15 minutes whose open PR (as the previews last looked it up in its directory, `@dev_pr`) `gh pr view` finds conflicting, or without any check in a repo with GitHub Actions workflows (`.github/workflows`). Checked once per idle stretch, after the round's other notes are out (gh may be slow), and only noted while the worker still rests in that stretch; while GitHub is still working out mergeability, again next round, and no note until it knows. A failed `gh` shows on the previews' bottom row and isn't tried again until the next idle stretch.
- `asks: <the question> (unanswered for 30m)`: a question its worker still waits on, resting, 30 minutes after it asked, then 1 h, 2 h, … after (one repeat for several waits missed while it worked or the previews were closed); the worker's next prompt answers it. A question its worker asked while the boss's inbox was off (or before the boss reopened) comes as a plain `asks` note on the first round after, while the worker still rests on it.
- `high context: 85% used`: a Claude worker whose context window is 80% full or more, from its status line (`dev statusline` records `context_window.used_percentage` in `@agent_context`). Once, then again only after its use drops below (`/clear`, compaction) and climbs back.

A worker that is itself a boss (one `dev boss <project> --background` started from a boss) sends its boss only what waits on the user and what went wrong: `waits on you: #4 ☐ on you: Merge #148? (options: Merge (Recommended) / Wait)` (the item's mark and who it waits on as its list has them when the note goes) when it adds an item for the user to its list (`dev todo add` without `--on`; `dev todo ask`), `asks`, `needs a decision` (its own dialogs), `failed` and `stuck`. Not its finished turns, its workers' notes, `high context` or `resumed`. One exception under the manager: a worker's `needs a decision` goes to the live manager too (`app-w (boss-app's worker) needs a decision: …`), which asks you and sends your pick to the worker itself, so you're asked once; the boss's note then ends `the manager asks the user: leave it to the manager`. With the manager closed, its inbox off, a boss you opened yourself or one under another boss, the boss relays it as before. A rate limit resumes it like a worker; till then (a minute past the resume time at most, and only while its boss is there to resume it) its own inbox waits, handed over with the resume prompt. `dev todo add --replaces` tells its boss too when it gives the item back (`--on me`) or changes its text. When you answer one of its asks other than through that boss (the phone page, a board, the sidebar, a shell), that boss gets `boss-app ask answered: #4 ☑ answered: "Merge #148?" on the phone page: Merge; drop its question: don't ask or relay it`, so the manager drops a question it would ask you.

Notes sit in `$XDG_STATE_HOME/dev/inbox/` (one locked file per boss), a worker's repeat note is dropped, and at most 20 wait (beyond them, a worker decision handed to the manager, which nobody else asks). They reach the coordinator in one batch: when it stops (its Stop hook blocks the stop with the notes, so it carries on), when you send it a prompt (added as context), or as soon as they're queued over Claude Code's [cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging) socket. For a rate limit with a reset time (from the hook's message, else the worker's screen), the note adds `dev resumes it at 19:11`: the boss's previews send the worker `Continue where you left off: …` a minute after the reset, if it's still idle with an empty input box and nobody prompted it since (`@dev_resume_at`, `@dev_resume_prompts`), and queue a `resumed` note. A closed boss's list tells the manager, naming the boss. None for a `--quiet` item or the owner's own tick (nor for a desktop-app boss; an unreachable inbox is warned on stderr).

Further coordination rules of the skill and prompts: a brief tells a worker to run gated commands (commit, push, merge, reset, kill, release) bare, with no pipe, chain or redirect; its CI wait is one loop that waits until checks exist and ends on all passed or any failed check; a boss chains `dev` writes with `&&` and reads the item back before announcing it; a saved draft is "requested" and its thread re-read in the same turn, none while a pick on that item is open; the manager labels relayed counts, money and sends "per boss-<project>" or "per <list> at HH:MM"; one restart item per list, its text bumped per release; a worker whose Codex review hits the usage limit merges with every other condition met and owes the review as an item, which a release and its ask name; a contract for an open design choice may carry an optional "Approaches" section; a text to a person rests on a premise its worker checked against records or repo docs and cites, its writer subagent gets the project's writing rules, and nothing is sent or pasted, or briefed to be, in the turn of a pick to send it: the boss runs a background `sleep 60`, ends the turn and sends once the later notes and the user's later words hold nothing against it; dev stamps the time on items and asks when added and on `dev todo note` notes (the start list shows `(added YYYY-MM-DD HH:MM)`, a note its date and time, the item view `added HH:MM (2h ago)`), so no current time is written there by hand; other clock times in briefs and records come from `date` (a past event keeps its source's time), and a release brief's done-when includes `gh release view v<X>` (or its host's release page); a brief carries the standing rules, the items already on the list it touches, shared hot files, the build or test recipe and where results go (never a tracked file); the manager asks at most 2 items per dialog while any boss works, and relays the notes it has first.

Each open item says when it may be out of date (⚠, its check): its linked PR (`--link` to a github.com PR; other links aren't looked up) merged or closed; approved, changes requested, checks green or failing since the item was added or replaced (against its lookup when the item was added or replaced (`add`, `ask` and `--replaces` look it up), so a PR already approved when the item was written doesn't flag it); its PR's lookups failing for 20 minutes (gh logged out, a PR gone: `dev todo check` prints why); unchanged for 2 days or more (an item's own age, not for an ask or a dated item before its `--until`: `add --replaces <n>` alone confirms it and starts afresh; one waiting for a person says `no action unless there is news`); or its boss closed. A `dev boss`'s previews look up its items' PRs every 15 seconds (its inbox on or off), two at a time, each at most every 10 minutes, keeping what they find in `$XDG_STATE_HOME/dev/todo/checks/` (not the list: its `updated` stays the boss's own last change; an unreadable checks file is dropped and rebuilt); `dev todo check` looks them all up now (a desktop app boss has no previews: it runs this). TO DO rows of your own items show the check at the right edge (`unchanged 5d`); an item whose PR moved sits under Check with it (`#412 merged 40m · reviewers`). `dev todo` and `--all` end the line with it (`⚠ PR #412 merged 40m ago`), after who is on the item, as the hooks' open lists say it (`the user is on it: <doing>`; on the boss's own `the boss is on it`, where they say `you are on it`), `--json` gives each item `added` and `check: {kind, pr?, since, waiting?}`, and the open lists the hooks give a boss put the items to re-check first, each with why (a worker session gone too), then `The rest:`. A boss's list stays after its session closes: `--all` (`--json`: `closed: true`) and the manager's TO DO keeps showing it, each item `boss closed` unless its PR moved, until the boss reopens under its name and takes it back; its rows can't be answered or gone to (a key says `dev boss <project>` reopens it), but `d` ticks one, and `dev todo done` and `check` take the closed boss by `--boss` while any session is open on its tmux server, as the closed lists are found through it (a live session by that name that is no boss is still refused). The manager's previews also look up the closed lists' PRs, two more at a time, so an item whose PR merged shows `#18 merged`, not `boss closed`; the manager's roll-up line counts the closed lists as its TO DO does: their items under Check and Boss closed count in neither `decide` nor `to do`, a closed boss's ask included, as nothing can answer it until the boss reopens. A list an older dev wrote doesn't name its boss: its file's name does (`<socket>-boss-<project>.json`), unless it holds `-boss-` again or ends in `-manager` (another socket's `default-boss-x` starts like `default`'s), or the name was hashed (unsafe characters); a list under a session id (from before lists were keyed by name) and a desktop app boss's stay out.

The boss is told too, once: a `dev boss`'s previews, while its inbox is on, queue a `to do` note in it (delivered like worker notes) for each open item whose PR merged, closed, got approved or changes requested, or turned green or failing since its first lookup, each move once; whose worker session is gone; and for each item unchanged for 2 days, again only after 2 more days without a `--replaces` (an item `--waiting-for` a person once only, worded `no action unless there is news`; its PR's moves still come): `to do #5 "Deploy the cache fix after #418 merges" (on Tomas): PR #418 merged 40m ago`. `--done-on merged|approved|green` (with `--link` to a GitHub PR) ticks the item by itself once a lookup finds its PR so (never from its text), and the boss gets `to do #8 "Second review of #415" ticked by itself: PR #415 approved (--done-on approved)`. dev also closes what its own state shows is over, by fixed rules only, never by an item's text: `--ends restart:<version>` once every coordinator running on the server (the manager, each `dev boss`) started fresh on that dev version or later (a coordinator's `SessionStart` on `startup` records `@dev_version` "<unix> <version>" on its pane; a `/clear` or resume doesn't, and a coordinator without it counts as not restarted), `--ends test:<version>` once an item with `--ends test:<newer version>` is on the same list; and the manager's "Clear the manager's context?" offer is withdrawn once the idle stretch it was put in ended (its state changed, or its session is newer than the offer; not while the manager's dialog shows it or your pick on it waits to be relayed, nor while a `dev agent clear manager` runs, whose end answers it), so the next stretch offers anew. The previews' rounds, `dev todo check` and each coordinator `SessionStart` (start, /clear, resume, compaction) run the `--ends` rules on its list (the manager's previews also on the closed bosses' lists); the offer's withdrawal runs in the manager's previews' rounds; such an item is ticked by `dev` with why as its result, shown in place of "decided for you" on the Done card of both boards and in the item popup (`closed by dev: restarted on v0.94.0`, `closed by dev: v0.94.0 replaced v0.93.0 (#12)`, `withdrawn by dev: the manager worked on`), never as your answer (no "you answered" note, no tally answer); the boss gets one `to do` note (the manager hears of a withdrawn offer in its next reminder, as a note would start its turn): `to do #3 "Test v0.93.0 by hand" closed by dev: v0.94.0 replaced v0.93.0 (#12) (--ends test:v0.93.0)`. Reopened, it isn't ticked again for the same restart or newer test, only a later one. An `--until` tick, every tick with the inbox off, and on a desktop app boss every tick (`dev todo check` ticks it) is told once in the boss's next reminder (with the inbox off, its next start or `/clear`). Notes and ticks don't change the list's `updated`. On a stale list's TO DO row the age is the item's own.

## Desktop worker board

```bash
dev desktop board [--json] [--boss <local_id>]   # a desktop app boss session's workers
```

Lists the unarchived sessions a Claude desktop app session started (default: `$CLAUDE_CODE_HOST_SESSION_ID`, the session it runs in): state (busy, blocked, idle, stopped), title, branch, PRs and context use; `--json` adds the app's verdict on the last turn and what it needs, the tool in flight, the last lines of the newest reply, and the app's `model` (its family, `opus`, `sonnet`, `haiku` or `fable`, else its id) and `effort` for the session (`""` when unknown). It joins the app's session records (`~/Library/Application Support/Claude/claude-code-sessions`), `~/.claude/sessions` and the transcripts; the context window comes from Claude Code's model catalog (`~/.claude/cache/model-catalog`). These are private app formats: a file that fails to parse is reported on stderr. So is a dev-board mod (`CLAUDE_CODE_PLUGIN_DIRS`) changed on disk since the boss's Claude started: it loaded the mod then and runs the older copy (not checked with `CLAUDE_CODE_PLUGIN_DIR_WATCH=1`, which reloads it). The [dev-board mod](mods/dev-board/README.md) shows it live in a pane of the boss session.

Each worker in `--json` carries `notes`, the health notes `dev boss`'s inbox has for tmux workers, each `{key, kind, text}` with a key that stays the same while its condition holds: `stuck` (busy with no progress for 15 min: no hook, transcript write or live status change), `needs a decision` (a dialog shown, by its `Notification`, or an `AskUserQuestion`, unanswered for 3 min while busy), `high context` (80% or more, once per conversation), `rate-limited` (its reset time, or `no reset time read`), `resume due` (reset passed a minute ago, not busy) and `wake due` (its planned wait ended, not busy; no `stuck` note before while its own background tasks run). A stopped worker has none. The hook-based ones come from the Claude hooks above: in a desktop app session (`CLAUDE_CODE_ENTRYPOINT=claude-desktop`, no `TMUX_PANE`) `dev state` and `dev question` write the session's state, its dialog's question and a rate limit's reset to `desktop/<session id>.json` in dev's state directory (`$XDG_STATE_HOME/dev`, else `~/.local/state/dev`) instead of a pane's options; `SessionEnd` removes it, and a session's start removes those unwritten for a week. A running worker without one is reported on stderr: its hooks run a `dev` without this.

It also carries `status`, finer than `state`, the first that holds: `stopped` (`statusText` saying so when a dialog was open as the app quit), `needs you` (a dialog waits on the person while busy, from that hook file, or, not busy, one was open when the app quit: `interruptedAwaitingPerson`), `waiting` in a planned wait (`until 16:30 · <why>`; busy, only while its own background tasks run before its time), `rate-limited`, `stuck`, `working`, `waiting` (a line `WAITING (…)` among its last few, a short sentence after it allowed: CI or a background job will wake it), `idle` on such a line `IDLE` (the newer of the two wins), `blocked`, `review ready`, else `idle`; `statusText` says what (the question, the tool, what it waits on, the reset time). `since` is how long it has been busy or idle (not running: since the app's last activity), e.g. `12m`; `ask` the question it waits on (a busy worker's AskUserQuestion, or, its turn over, the `ask` its last `wrap_up` ended on with its reply labels as options, `reply: true`, until a prompt comes); and `plan` its task list, `{content, status}` per step, replayed from the transcript's `update_plan` calls (`items` sets it, `advance`, `done` and `start` move it, `wrap_up` checks it off; a call whose result is an error changes nothing).

## Session cost

The sidebar shows each Claude session's estimated cost (`idle · $1.24 · title`), and `dev agent list --json` reports it as `cost_usd`. The number is Claude Code's own `cost.total_cost_usd`, the list-price estimate `/cost` shows. It covers every API call of the conversation, and resets on `/clear`. It isn't your bill on a subscription plan. `dev statusline` records it from the status line input, so run your status line through it:

```json
"statusLine": { "type": "command", "command": "$HOME/go/bin/dev statusline -- $HOME/.claude/statusline.sh" }
```

Without a command, `dev statusline` prints the cost as the status line. Codex panes show no cost.

A boss's total (its sidebar roll-up line, its board card, `cost_total_usd` in `dev agent list --json`) keeps what ended under it while the boss session lasts: a conversation's last cost goes to a ledger when it ends (Claude's `SessionEnd`: a `/clear` or an exit; the boss's own go to its own ledger, a worker's to its starter's), and a session closed for good (`dev agent close`, the sidebar's `×`) moves its live cost and its own ledger to its starter's. The board card and the desktop board show the closed part beside it, `$54.93 · $20.71 closed` (`cost_closed_usd`). A conversation resumed later counts live, not twice. The ledgers are in `$XDG_STATE_HOME/dev/spent/`, one per session something ended under (in practice its boss), keyed by the tmux session and its creation time: a boss reopened starts from zero. A ledger that can't be read hides the total: ⚠ on the roll-up, `cost_error` in place of the total in `--json`, `⚠ cost not read` on the desktop board. A close goes ahead when its cost can't be kept; its archive record says so. A session killed outside dev (`tmux kill-session`) or a crash loses its last cost; so does a worker whose starter was closed before it (`dev state` says so).

On a subscription plan, hide it from the sidebar, boss previews and `dev agent` text output (`--json` keeps `cost_usd`). Set on one session, it hides that session's cost wherever it shows. `dev statusline` without a command still prints it:

```bash
tmux set -g @dev_cost off           # or per session with -t
```

## Images in tmux

Claude Code draws images (pasted image thumbnails) with kitty graphics, but writes them to tmux without the passthrough wrapping tmux needs: tmux drops them and sets them as the pane title (`Ga=d,d=I,i=2,q=2`). So dev starts claude (new sessions, the boss, `dev resurrect` resumes) under `dev pty-wrap`, which runs it on its own pty and wraps each graphics sequence for passthrough; everything else passes through unchanged. Images show in a terminal with kitty graphics (Ghostty, kitty) given:

```bash
tmux set -g allow-passthrough on
```

and `"CLAUDE_CODE_FORCE_TERMINAL_IMAGES": "1"` in the `env` of Claude's `settings.json` (inside tmux Claude Code turns images off otherwise). A claude you start by hand runs unwrapped; wrap it with `dev pty-wrap -- claude`. In the wrapped pane, tmux's `pane_current_command` is `dev`.

## Remote Control names

dev starts claude (new sessions, the boss, `dev resurrect` resumes) with `--remote-control=<session>`, so in Remote Control each shows as its tmux session (`dev-flaky-tests`, `boss-dev`) rather than a title made from its first message; a resume keeps the name. This turns Remote Control on for those sessions even without `remoteControlAtStartup`. Workers (sessions `dev agent start` opens from a tmux pane, marked `@dev_started_by`, and their `dev resurrect` resumes) start without it, so a busy boss doesn't flood your phone with Remote Control notifications: with `--settings '{"remoteControlAtStartup":false}'`, which outranks that setting in your user settings; `/remote-control` still turns it on in one. A worker started by a plain session (not a boss) loses its `@dev_started_by` across `dev resurrect`, so it comes back with Remote Control. dev doesn't use `--name`: it would pin the pane title to the session name, and the sidebar and boss previews would lose the task title Claude sets there. Codex, Grok and agy panes start unnamed.

A proof or test run of dev on a private tmux server (`tmux -L <name>`) runs with `DEV_PROOF=1` in the environment of every `dev` run (export it before the server starts, so its panes inherit it): the first `dev` then restores no saved sessions (it only sets `@dev_restored`) and every claude it starts runs without Remote Control, so nothing shows on your account. Point the private server at its own snapshot directory too (`tmux -L <name> set -g @resurrect-dir <scratch dir>`, or a scratch `HOME`): a close there saves a snapshot, which would replace the live `last`. Never touch the live server.

## Phone page

`dev serve` serves the bosses' to do lists (what `dev todo --all --json` shows) to a page you open in the phone's browser. The page and the lists stay on the Mac: no app, account or outside service.

```bash
dev serve          # prints the URL to open on the phone (dev boss starts one on this Mac only, below)
dev serve pair     # in a real terminal (not a Claude session): prints the URL and a one-time code
dev serve pair --popup  # the manager's Claude, when you ask it: the same in a popup on your client, never in its output
```

`--popup` runs only in the manager's coordinator pane, once per prompt of yours there, on the most recently active client showing the manager (refused with none). It says whether the popup showed a code; one that didn't show or said it showed none (another popup open, no `dev serve` running) gives the prompt back, one closed before saying keeps it. The popup runs `dev serve pair` and stays until Enter; the code shows only there, not in the command's output, the transcript or tmux, and no file holds it in plain text (`pair.json` keeps a salted hash).

`dev boss` (a project's boss, the manager, `--background` too; not `--adopt`; not a boss opened from `dev`'s picker) starts `dev serve` when none answers (on a loopback address, when none answers there: beside the launchd agent's tailnet one, whose address can go): detached in its own session, so it outlives the boss and tmux, with `--awake=false` (no keep-awake), on `127.0.0.1:8417`, this Mac only (a hand-run `dev serve` keeps its own default, below), or `DEV_SERVE_ADDR=ip:port` (a port, not 0), reading the boss's tmux server, logging to `$XDG_STATE_HOME/dev/serve/serve.log`. It prints `dev serve started: http://…/ (this Mac only, no pairing needed)` on the terminal (for a tailnet or LAN `DEV_SERVE_ADDR`: `(pair a phone: dev serve pair)`, and on a LAN address the plain-HTTP warning) before the boss attaches (seen after you detach); a start that fails (a taken port) prints one `⚠ dev serve not started: …` line, one that starts but doesn't answer within 3 s a `⚠ dev serve: started, not answering` line, and the boss opens anyway. One already answering (on loopback, there) is left alone (one on another version gets a `restart it to update, unless it reloads itself` line), and so is one that runs but doesn't answer (hung, or its recorded address gone: each `dev serve` holds a lock on `serve/alive` while it runs; on loopback only while something holds its port), with a line saying so; two bosses starting at once take turns (a lock on `serve/start`). It starts nothing with `--no-serve` or `DEV_NO_SERVE=1`, when the launchd agent below is installed (on loopback: only one on that address; it prints the `launchctl kickstart` line instead, and the `bootstrap` one for an agent not loaded yet), or when the boss runs on a tmux server other than the default one unless `DEV_SERVE_ADDR` is set (it says so in a line). It never pairs: on loopback none is needed (below); on a tailnet or LAN `DEV_SERVE_ADDR` pairing stays `dev serve pair`. To stop it, kill it (`pkill -f 'dev serve --awake=false'`, which also matches a launchd agent installed with `--awake=false`). A hand-run `dev serve` doesn't match that: stop it with Ctrl-C in its terminal, or `pkill -f 'dev serve( |$)'`, which stops every one (and anything else whose command line holds `dev serve`, `dev serve pair` too). On loopback nothing else on the network reaches it, and a browser on this Mac gets the board with no pairing.

For a phone, run `dev serve` by hand (beside the autostarted one: each `dev serve` records its own address, under `serve/addr/`), or set `DEV_SERVE_ADDR` to a tailnet or LAN address (on a tailnet or LAN address `dev boss` starts one only when no `dev serve` answers, so not beside the autostarted one): the one `dev boss` starts is on this Mac only. Open the printed URL on the phone and enter the code (8 digits shown as `1234 5678`, valid 5 minutes, once; 5 wrong tries void it); the phone stays paired. Pairing is required on a tailnet or home network address. The URL is the address the running `dev serve` listens on; with several running, pair names each one a phone can reach (the code works on any of them); with no `dev serve` running, pair errors. If `dev serve` listens on loopback only (`--addr 127.0.0.1:…`), a phone can't reach it and a browser on this Mac needs no pairing: pair writes no code, says so, gives the URL and how to restart it for a phone. There the board, its stream and the actions refuse instead a request a browser marks as another origin's, another port included (`Sec-Fetch-Site` other than same-origin or none, or an `Origin` other than the page's own: 403), reads too, besides the Host check every bind has; a process on this Mac (curl, an agent, another user's) is not refused there, nor is anyone reaching the port through a tunnel or forward to it (`ssh -L`, `socat`): don't forward a loopback `dev serve`. A `dev serve` from an older dev still wants pairing on loopback: pair says to restart it. After a release is installed, `dev serve` reloads itself in place (same pid, same address; a page's event stream ends and it reconnects): it checks its binary every 10 s and reloads once the file holds another release tag that answers `--version`. It takes no part in the sidebars' canary: a canary pane that died holds the panes on the old version, not `dev serve`. A phone action still running 5 s into the reload holds it until the next check. A failed reload keeps it serving the old version with a `❌ reload:` line, and it stops watching until restarted; `tmux set -g @dev_reload off` (on the tmux server `dev serve` reads: the default one, or the one it was started in) or `DEV_NO_RELOAD=1` turns reloading off. An older `dev serve`, from before it reloaded itself, must be restarted by hand: it rejects codes the new `dev serve pair` writes. It listens on the Mac's tailnet address when it has one (the phone then needs Tailscale too), else on its home network address: then the phone must be on the same Wi-Fi, and since it is plain HTTP, other devices on that network can read the traffic, so use it on a network you trust (no TLS yet). `--addr ip:port` picks the address.

- Cannot: push notifications, desktop app bosses' asks (shown read-only), adding items.
- `--awake` (default on): holds a no-sleep assertion (`caffeinate -s`) while serving, which macOS honours on mains power only; on battery it says the Mac may sleep. A closed laptop lid still sleeps.
- `dev serve --install [--addr ip:port]` writes `~/Library/LaunchAgents/dev.serve.plist` so it runs at each login (on tmux's default server), and prints the `launchctl` line to start it now; `dev serve --uninstall` removes it and prints the `launchctl bootout` line. It picks its address when it starts (a reload keeps it): when the Mac's address changes (another Wi-Fi, Tailscale up later), or after updating a `dev serve` from before it reloaded itself, run the printed line again.
- `dev serve unpair [device]` drops one phone's session, or every one, at once.

## Reload on a new release

After a release is installed, the sidebars and each boss's previews pane reload themselves in place (same pid, same pane), as `dev serve` does: each checks its binary every 10 s and reloads once the file holds another release tag that answers `--version` (a local build never counts), the panes a few seconds apart. One pane goes first (the canary); the others follow once it has run 30 s on the new version. A pane reloads only when idle: no answer running, no reply box or kill question (y/n) open, not in TO DO mode, no action running; the previews also wait while a kept reply is too long to carry. Meanwhile its bottom row says so (the sidebars: `↻ <version> ready: reloads when idle`; the previews: `↻ <version> reloads when idle`, `… after TO DO (esc)`, `… after answering …`, `… once the long kept message goes`), and `↻ dev <version>` for 10 s after. The previews keep their selection, folds, expanded cards, kept replies and width. A reload that fails leaves the pane on the old version with a `❌` line on its bottom row. A canary pane that died holds the others on the old version (warned after 60 s): unset `@dev_reload_canary_<version>` or set `@dev_reload_ok` to the version to move on. `tmux set -g @dev_reload off` or `DEV_NO_RELOAD=1` turns reloading off.

## Sidebar width

Every sidebar shows the same width, kept in the global tmux option `@sidebar_width` (default 40). Drag any sidebar's border (or `resize-pane` it) and every other sidebar follows; new sidebars open at that width. When tmux rescales panes because a window resizes (another client size, a terminal resize), each sidebar takes the stored width back instead of drifting. Compact mode's zoom leaves it alone.

## Sidebar branch

The sidebar shows an agent session's branch right of its name, cut to the columns the name leaves, unless the session is named after it (`<project>-<branch>`, `/` as `-`, as a worktree's is): `dev` on `main` shows `main`, `dev-fix-login` on `fix-login` shows none.

The second line ends in the agent's title, cut to fit. The selected session shows a cut title whole, wrapped on lines of its own below, while every session still fits the sidebar's height.

## Sidebar PR links

When the [GitHub CLI](https://cli.github.com) (`gh`) is installed and signed in, the sidebar looks up each agent session's PR (`gh pr view` in the agent pane's directory, so fork PRs count; in the background, only while the sidebar's session is on screen, cached for a minute per directory and branch in the agent pane's `@dev_pr` option, which every sidebar and the boss previews share; the `dev state` `PostToolUse` hook bumps the pane's `@dev_pr_gen` after a `gh pr create`, `merge`, `close`, `reopen` or `ready`, so the tag shows as soon as gh answers) and leads the session's second line with it, e.g. `#12 open`. State is one of `open`, `draft`, `merged`, `closed`. No `gh`, no remote, or no PR shows nothing.

`o` on the selected session (else the current one), or a click on its tag, opens the PR in the browser (`gh pr view --web`); when the lookup failed, `o` shows why.
